# 테스트 케이스 명세 — 커플 공유 일정관리 (압축판)

> 기준: [`requirements.md`](./requirements.md) / 작성일: 2026-05-29 / 개정: 2026-05-29 / 상태: 확정
> 코드가 아니라 **무엇을 검증할지** 글로 정리한 문서다. 구현 시 이 케이스를 테스트로 옮긴다.
>
> **개정 배경:** 초안 ~50개는 1인 사이드 프로젝트엔 오버스펙. [`study/test.md`](../../study/test.md)의 피라미드 원칙
> *("규칙을 잡을 수 있는 가장 좁은 테스트를 고른다")* 에 맞춰 핵심 16개로 압축했고,
> 이후 **헤어짐/삭제 기능을 이번 스프린트 범위에서 제외**(README '안 하는 것')하면서 관련 4개(헤어짐 전이·잠금 판정·종속 삭제·잔여 윈도우)를 덜어내 **핵심 12개**로 확정했다.
> 덜어낸 것은 본문 끝 [부록 B](#부록-b-덜어낸-케이스와-근거)에 근거와 함께 남긴다.

## 압축 원칙

1. **싸고 핵심을 증명하는 것부터 채운다.** 도메인 단위 테스트는 밀리초짜리이고, *"도메인은 순수 → DB 없이 테스트"* 라는
   이 프로젝트의 아키텍처 주장(CLAUDE.md)을 그대로 증명한다. → 1순위로 복원·압축.
2. **비싼 통합/E2E는 대체 불가능한 것만.** 동시성 락, 게이트 스냅샷처럼 *계층이 맞물려야만* 드러나는 것만 남긴다.
3. **단순 @Valid·CRUD·렌더링 응답은 짜지 않는다.** Swagger/Postman으로 손으로 찔러본다.
4. **데드락 정밀 재현은 테스트가 아니라 코드리뷰**로 갈음한다(잠금 순서 PK 오름차순 고정).

## 표기

- **[단위]** 순수 도메인 단위 — 프레임워크/DB 없이 객체만으로(예: `Couple.connect()`).
- **[@DataJpaTest]** 영속 계층 슬라이스 — 실제 SQL·제약·매핑.
- **[@WebMvcTest]** 웹 계층 슬라이스 — 보안필터(401/403)·상태코드. Service는 mock.
- **[@SpringBootTest]** 전 계층 통합 — 동시성·트랜잭션 경계·전체 흐름.
- `(FR-x)`는 근거 요구사항. `(원 ID)`는 초안 케이스 추적용.

## 1. 도메인 단위 [단위] — ⭐⭐⭐ 가장 싸고 핵심

> 묶음(parametrize)으로 한 테스트에 여러 케이스를 담아 개수를 줄인다.

### T1. 연결 상태 전이 (원 C-U1·C-U2·C-U3)
- `PENDING`에 `connect()` → `CONNECTED`, `connected_at` 기록 (FR-2.3)
- `CONNECTED`에 `connect()` → 거절(불변식 위반) (FR-2.3)
- `requester_id == target_id` 커플은 생성 불가(자기 연결 금지) (FR-2.2)

### T2. PENDING 만료 판정 — 경계값 (원 C-U4·C-U5)
- `created_at`+10분 **미만**은 "유효", **정확히 10분/초과**는 "만료" (FR-2.7)

### T3. 색상 매핑 (원 C-U12·C-U13)
- `MINE`→본인 `personal_color`, `PARTNER`→파트너 `personal_color`, `COUPLE`→`couple_color` (FR-7.4)
- 미설정 시 서버 기본색으로 매핑 (FR-7.1, FR-7.2)

### T4. 일정 불변식 + UTC 절대시각 (원 S-U2·S-U5)
- `end_at < start_at` 거절, `end_at == start_at` 허용(경계값) (FR-4.1)
- 시각은 `Instant`(UTC)로 저장되고, **서로 다른 오프셋 입력이라도 UTC 절대시각 기준**으로 `end>=start`를 판정 (FR-4.5)
- `visibility=COUPLE`이면 `couple_id` 필수(없으면 거절) (FR-4.3)

### T5. 캘린더 category 판정 + 파트너 PRIVATE 제외 (원 S-U7·S-U8)
- `owner==me`→`MINE`, `couple_id==내커플 && COUPLE`→`COUPLE`, `owner==파트너 && SHARED`→`PARTNER` (FR-5.4)
- 파트너의 `PRIVATE`는 어떤 category에도 매칭되지 않아 결과에서 제외된다 (FR-5.3, FR-5.4)

### T6. 비밀번호 정책 (원 U-V2·U-V3)
- 9자 이상 **+ 영문·숫자·특수문자 3종 모두** 포함해야 통과. 하나라도 빠지면 거절 (FR-1.10)
- *근거: @Valid 한 줄이 아니라 커스텀 정규식 조합이라 깨지기 쉽다. 단위 테스트가 가장 싸다.*

## 2. 영속 계층 [@DataJpaTest] — ⭐⭐⭐ mock으로 못 잡는 영역

### T7. 이메일 결정적 암호화 조회 (원 U-I4·U-I5)
- 같은 평문 email은 항상 같은 암호문 → `WHERE email_enc = ?`로 조회된다 (FR-1.2)
- DB에 email **평문 컬럼이 존재하지 않는다**(보안 불변식) (FR-1.2)

## 3. 웹 계층 / 접근 게이트 [@WebMvcTest] — ⭐⭐ 보안 게이트 주력

> 보안 필터 단에서 JWT `coupled` claim으로 판정. `spring-security-test`의 `jwt()`로 claim을 흉내낸다.

### T8. 게이트 차단/허용 (원 G-I2·G-I6)
- `coupled=false` 토큰으로 앱 기능(일정 API) 접근 → 403, 단 커플 연결 API는 허용 (FR-3.2)
- `coupled=true` 토큰은 앱 기능 통과 (FR-3.1)

### T9. 구 토큰 차단 — claim 스냅샷 (원 G-I4)
- 연결 직후라도 옛 토큰(`coupled=false`)이면 차단, 재발급(FR-1.6) 후 통과 — claim은 스냅샷, TTL로 수렴 (FR-3.3)

---

## 4. 전 계층 통합 [@SpringBootTest] — ⭐ 대체 불가능한 것만

### T10. 상호확인 연결 흐름 (원 C-I3)
- Y→X PENDING이 이미 있을 때 X가 코드 입력 → **새 행 없이 그 행을** `CONNECTED`로 전이하고 `couple_profile`이 생성된다 (FR-2.3, FR-7.3)

### T11. 동시성 락 — row 1개 보장 (원 C-I8)
- 두 유저가 동시에 서로의 코드를 입력해도 비관적 락(`PESSIMISTIC_WRITE`)에 의해 최종 커플 row는 **정확히 1개** (FR-2.6)

### T12. JWT claim 발급 + Refresh 갱신 (원 U-I9·U-I11)
- Access Token claim에 `sub=public_id(UUID)`, `role`, `coupled` 스냅샷이 정확히 박힌다 (FR-1.4)
- 유효한 Refresh Token으로 새 Access Token 발급 시 `coupled`가 **현재 상태로 갱신**된다 (FR-1.7)
  → T9(구 토큰 차단)가 "재발급 후 통과"로 수렴하는 **전제 메커니즘**

## 부록 A: 테스트가 아닌 검증 (코드리뷰)

- **데드락 방지 (원 C-I10):** 두 유저 PK **오름차순 정렬 후 락 획득**으로 교차 요청 데드락을 구조적으로 차단.
  정밀 재현 테스트는 flaky·고비용이라 짜지 않고, 잠금 순서 고정을 코드리뷰로 검증한다([`concurrency.md`](../../study/concurrency.md)).

## 부록 B: 덜어낸 케이스와 근거

> "짜지 않는다"는 곧 "검증 안 한다"가 아니다. **Swagger UI / Postman으로 개발 중 손으로 찔러본다.**
> (헤어짐/삭제 계열은 "검증 안 함"이 아니라 **기능 자체가 이번 스프린트 범위 외** — 아래 마지막 행.)

| 덜어낸 것 | 원 ID | 근거 |
|---|---|---|
| 단순 입력 검증 (이메일 형식·길이, 닉네임, couple_code, HEX 등) | U-V1·V4·V5·V6·V7 | `@Valid` 한 줄로 끝. MockMvc로 테스트하면 프레임워크를 테스트하는 꼴 |
| 가입 happy-path·BCrypt 저장·코드 자동발급/충돌재생성 | U-I1·I2·I6 | JPA/인코더가 보장. 눈으로 1회 확인이면 충분 |
| 코드 재발급 분기 (정상/충돌 상태/만료) | U-I15·I16·I17 | 단순 상태 조회 분기. 핵심 리스크 아님 |
| 내 정보 조회 응답 필드 | U-I13·I14 | 렌더링용. Postman으로 눈으로 확인 |
| 로그인 성공/실패·토큰 부재 401 | U-I7·I8·I10 | 표준 시큐리티 흐름. T8·T12에서 간접 커버 |
| 단방향 PENDING 생성·없는 코드·만료 재생성·free 제약 | C-I1·I2·I4·I5·I6·I7 | T10(상호확인)·T1·T2의 단위 규칙으로 커버되는 분기 |
| 광클 단일 유저 중복 방지 | C-I9 | T11(동시성 락)가 메커니즘 자체를 보장 |
| 등록 권한·visibility별 조회 happy-path | S-I1~I10 | 단순 CRUD/필터. 판정 규칙은 T4·T5 단위로 커버 |
| **헤어짐 전이·잠금 판정·종속 삭제·잔여 윈도우 (기능 제외)** | C-U6~U10·C-I11·I13~I18·G-I5 | **헤어짐/삭제 자체가 이번 스프린트 범위 외**(README '안 하는 것'). 추후 스프린트에서 케이스 복원 |
